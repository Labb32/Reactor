# 이전 및 배포 준비

버전 번호는 변경하지 않았다. M5 검증 후보는 M4 정리 브랜치의 최종 코드 커밋으로 고정한다. 실제 빌드·패키징·릴리스·태그·push·서버 배포는 수행하지 않았다.

## 업그레이드

1. 기존 실행 파일·설정·DB와 Workspace별 복원 지점을 확보한다. schema 9에서는 기존 버전에 맞는 SQLite 일관 백업을 별도로 준비한다.
2. 유지보수로 신규 작업을 막고 daemon을 정상 중지한다. 살아 있는 Agent·복구·삭제 작업을 해소한다.
3. 새 바이너리를 별도 위치에 준비하고 경로와 실행 계정 권한을 확인한다. Linux system service는 사전에 만든 비root 계정과 그 계정 소유 config/data 경로를 사용한다. Agent 설치·로그인·PATH는 별도로 준비한다.
4. 초기화 시 schema 9→10은 pre-v10 SQLite 백업을 만들고 Task 관련 필드를 추가한다. 활성 lease가 있으면 이전을 거절한다. 기존 승인·예약·이력을 보존한다.
5. 서비스 등록·readiness·Workspace prepare·Agent 세션·격리를 확인한다. 유지보수 해제와 실제 작업 재개는 운영자가 명시적으로 수행한다.

## 되돌리기

새 schema 파일을 구버전 바이너리에 그대로 연결하지 않는다. 서비스를 중지하고 업그레이드 전 바이너리와 그 시점에 일관되게 보관한 DB·설정을 함께 복구한다. 새 버전의 backup restore는 지원 schema와 format이 일치하는 백업만 사용한다. pre-restore 보관 디렉터리는 원본 파일 보관이며 자동 rollback 실행기가 아니다. Workspace/Git/세션 복원은 각각의 전략을 따른다.

## 검증과 배포

M5에서 Linux 우선으로 실제 CLI·세션·worktree·프로세스 종료·경고·retry·마이그레이션·백업/복원·서비스 재부팅을 확인한다. Windows Job/ACL과 다른 플랫폼은 별도로 검증한다. 검증 전 운영 사용 가능으로 표시하지 않는다.

기존 release workflow의 버전/태그 검사와 플랫폼별 패키징을 유지한다. 배포 패키지에 운영·이전 문서를 포함한다. 실제 배포 산출물 생성은 별도 빌드 허용 후 진행한다.
